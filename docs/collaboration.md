# Document collaboration across nodes

Two people editing on the same node share one live room. Their edits are also written to `drive_room_update` for that file and generation. Those rows replicate with the rest of SuiteDB. A person whose name contains a line break is listed as Someone. The stored name stays.

A person who opens the file on another node, after that log has arrived, is given the document rebuilt from those rows. A room that is already open on that node reads the new rows on its sweep and sends the added text to the person who is already connected. That sweep is every 30 seconds. A test may set it shorter. The same log carries a ProseMirror fragment: bold text, a table cell, and an image whose source is the picture's embedded data. That data is the same on the other node. When the room is saved, those bytes stay in the file and the file opens again. A source that is only a file name is left out of the saved file. Stopping a node after an edit is in that log, then starting it again, still has the edit when the file is opened. Dropping one person's connection does not remove an edit that was already stored. Sending that same stored edit again does not repeat its text, and the log keeps one row for those bytes. The second send is still acknowledged. `Beds` stays `Beds`. A session whose expiry date has passed cannot open the room. An already open socket is closed on its next message, and that message is not applied. Removing someone's grant does the same: the next message on that socket is not applied, the socket closes, and a later read of the file is refused. The check waits for that next message. The stored text remains for someone who still has access. Two people can open the file on another node at the same time. If they open after the log has arrived, both see the saved edit immediately. If they open before it arrives, both see that edit once the log reaches their node. A local edit that was never written to the log is not part of what a restarted node or another node rebuilds. A caret is a pair of positions. Maya's caret at 1 through 4 is given to Sam, and the paragraph is not changed. A caret message that also carries the paragraph text is not used as the caret on the client. The shared editor draws that caret as a mark named Maya. The paragraph text stays `Tomatoes are in`. That mark was drawn in a test view, not in the SuiteLeaf window. The browser keeps that edit until the node answers. An acknowledgement means the edit is in the log. The journal row is written before the live room changes. A new room on the same database reads `Beds` from that row. A refusal means it was not stored, and the browser does not send it again. The answer names the edit's id and not the document text. An edit that was sent and then lost with the socket is sent again. When the last person leaves and there is no saved file to write into, the open text stays in the room. The sentence `Tomatoes are in` is still there after both people leave. The room is not emptied first and then found to have nowhere to write. Undoing one person's paragraph removes that paragraph and leaves the other person's paragraph. Maya's `Tomatoes are in` can be undone after Sam adds `Beans are staked`, and both then see only `Beans are staked`. The same undo function the shared editor uses for Mod-z and the toolbar removes `Tomatoes are in` and leaves `Beans are staked`. That check called the function. It did not press the toolbar or a key. This was not typed in two browsers. A viewer joins that room and is given the same text. A viewer's own edit is not applied. Removing the viewer's grant still closes the socket on the next message. The web client opens that room for a viewer. The editor stays read-only, and the client does not copy the viewer's open paragraphs into the shared document. The editor is attached when a joined message says the room is shared. When a second person arrives, the person who was already there receives that joined message again, so a viewer who opened the file alone is attached without joining a second time. This was not opened in a browser.

A commenter may add a comment. Labeling a paragraph or a sheet cell as a comment does not apply it. The check copies the room, applies that update there, and leaves the live room unchanged when the paragraphs, the ProseMirror fragment, or the cells, slides, or lines maps would change. A document attribute other than the comment list is treated the same way. A commenter may store `Water the beds` on the comment list. A paragraph style labeled as a comment is not stored, and `secret-value` is not left on the room. Another map, such as a form, is also left unchanged. Text in another fragment is compared too. A notes fragment that says `secret-value` is refused, and that word is not left on the room. XML text stored on a map or in a list is compared too, even when the restored root has no type tag. Changing `Beds` and `North` to `secret-value` is refused, and that word is not left on the room. The comment text `from a comment` still arrives. The refused paragraph and cell contain `secret-value`, and that word is not in the live room. `cargo test -p suiteleaf-node --bin suiteleaf-node -- a_viewer_or_commenter_cannot_change_the_live_document` passed. This was not typed in two browsers.

The first seed of an empty room stores `Tomatoes are in`. A second seed of that same sentence, built as its own document, is not applied, so the sentence stays once. A later paragraph update still adds `Beans are staked`. The socket handler treats a seed message as a seed even when the message also names a paragraph. This was not typed in two browsers.

A second person who already has the room text does not copy their open file over it. The room held `Tomatoes are in` and `Beans are staked`. The open file also named `secret-value`, and that word was not written into the room. An empty room still receives the open file, so the first person can seed `Tomatoes are in`. When the shared fragment is empty and the room already has paragraph text, the editor follows those paragraphs. `npx vitest run tests/collab-seed-local.test.ts` passed (2 tests). This was not typed in two browsers.

The browser auth message includes `protocol` 1. A message with no protocol number is also protocol 1. Protocol 2, or a protocol that is not a number, is refused with `This app speaks collaboration protocol 1.` That sentence does not include the value that was sent. A query token on the socket address does not carry a protocol number and is still accepted. A later join message also sends protocol 1. A join whose protocol is `secret-value` is refused with the same sentence, and the room is not joined. The browser stops retrying and says `This app speaks collaboration protocol 1.` That sentence does not include `secret-value`. This check was not opened over the network.

While an edit is waiting to be stored, the document says so. Hiding the tab leaves that edit in place. If the socket then drops, the notice says the edit is still on this device, and the next connection sends it again. The notice does not include the paragraph or the token. If the room refuses the token, the notice says to sign in again and does not include the token. That pause keeps the waiting edit. Signing in again opens the room and can send it. A lost grant still stops the room. If access is gone, the notice says you no longer have access. The SuiteLeaf window was not opened.

An edit that is still waiting is written in session storage for that file. Opening the room again reads it back and can send it. The stored update keeps the edit bytes. A stored value that is not a list is removed, and that text is not thrown. The notice still does not include the paragraph or the token. The edit is not on another node until that node stores it.

Undo of a local bold mark and a local picture leaves the other person's paragraph and the earlier text. The bold is removed and the picture is removed. The other person's paragraph stays. Undo in a shared document drops the newest waiting edit and leaves a seed in place. An update already handed to the socket stays. The dropped bytes are not returned. A second undo does not remove the seed. The SuiteLeaf window was not opened.

Someone whose last beat is within 5 seconds is editing or viewing. A beat older than 5 seconds and still within 15 seconds is idle, so Jordan's chip says `Jordan is idle` even if the beat said editing. A name with a line break stays one line, so `Ada` and `Lovelace` say `Ada Lovelace is editing`. A blank name says `Someone is idle`. A beat older than 15 seconds is left off the list. The file title is not part of that chip. A stored presence time of 0 does not count as idle, so that person stays in the room and the open text stays. The SuiteLeaf window was not opened with two people.

A dropped socket waits 200, 400, 800, 1,600, 3,200, and then 6,400 milliseconds. A later try stays at 6,400. A delay that is not a number waits 200 milliseconds. That wait does not include a token. The room address drops a user, a password, a query, and a fragment. `https://user:secret-value@leaf.example/app?token=secret-value` becomes `wss://leaf.example/api/drive/items/file-1/session`. A page address that is not a web address says `The collaboration address is not a web address.` and does not repeat the text. Queuing the same update id again keeps the first copy. The later bytes are not stored. Loading a saved queue does the same: the first copy stays and the later copy is not stored.

Spreadsheet and slide collaboration are separate from this document room.

A comment thread is stored on the shared room beside the fragment. Compaction keeps the quote `ripe` and the message `Water the beds` with the paragraph. A stored value that is not a list of threads is left out. An attribute `012` stays `012`. A heading level `1` stays the number 1.
