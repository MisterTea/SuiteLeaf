# Why you can open a file

`GET /api/drive/items/{id}/explanation` returns the same decision as the role check, for the signed-in person only. The reason is one of administrator, owner, a grant, an expired grant, a restricted folder, or no grant. A restricted folder keeps its own grants and blocks grants from the folders above it. The sentence names that folder when the person can open the folder above it, and it does not include the folder id. When they cannot open that folder, the request says the file was not found, the same as a missing file. A person with no grant gets that same result. The file name and id are not in it. Other people's grants are not in this response.

The share dialog shows one sentence from that reason. A grant id is not repeated in the sentence. A membership cycle is mentioned without listing every group. A folder walk that stops at the depth limit says the chain was too deep to finish.

`POST /api/drive/items/{id}/move-preview` compares the item and destination explanations that were approved with those explanations now. A difference refuses the move. The response still names the access the caller would have after the move: a direct grant stays with the item, and access that came from the old folder is replaced by the destination. An expired grant on the file does not hide a live grant on the destination. The caller would be an editor from that folder. When the destination has no role, the expired grant stays and the role stays none. The route does not move the file. Other people's grants are not included.

`plan_restrict` lists each person who would have a different role on the folder or a file inside it if the folder became restricted. A user grant, the people in a group grant, and the people in an organization grant on a folder above it are included. The organization id itself is not listed as a person. The plan names how to clear the restriction. Grants are not deleted, so clearing it returns the earlier access. The plan does not change the folder. `restrict_folder` writes that same plan down and then sets the restriction. `restore_inheritance` clears it.

`plan_member` lists the files where a person's role would change if they joined or left a group. Adding Sam to Garden club would make Sam an editor of the watering rota. Sam's role stays none. Removing Priya would take that editor role away. Priya stays an editor. An empty name says to name the person. The plan does not include the file body. Nothing is written. `POST /api/admin/groups/{id}/member-plan` returns that plan for an administrator. Someone who is not an administrator is refused. The plan was requested on a running node. Adding the group Volunteers, which contains Sam, to Garden club would make Sam an editor. Priya, who is already in Garden club, is not listed again. Removing Volunteers would take Sam's editor role away and would leave Priya's role. Nothing is written until the plan is applied. The group page has a Preview button beside Add person and beside Add group. The sentence names the file and the role change, leaves out ids, and says nothing is changed. A role that is not viewer, commenter, responder, editor, or owner is `another role`, and that other word is not repeated. The Admin page was not opened in the browser. `commit_member` writes the membership only when that plan still matches. A plan that says viewer, while the live plan says editor, is refused with `The access plan changed. Review it again.` and Sam stays without a role. The matching plan makes Sam an editor. The refusal does not include the file body.

`POST /api/admin/groups/{id}/member-commit` writes that reviewed plan. The group page shows Apply reviewed plan after the preview. A refusal that is not the plan-changed sentence says the reviewed plan was not applied, and does not repeat a secret. The route was not requested over the network. The Admin page was not opened in the browser.

An open collaboration socket is checked again on its next message. If the grant is gone, that message is not applied and the socket closes. A later read of the file is refused. The socket stays up until that next message.

`share_guest` shares one person as a viewer or a commenter until a UTC end date. An end written with an offset is stored in UTC: `2099-02-28T23:00:00-05:00` is `2099-03-01T04:00:00.000Z`. An offset that is not a real zone is refused with `A guest share needs an end date.` and the offset is not repeated. An editor role is refused. A missing or past end date is refused, and the existing role stays. A day that is not on the calendar, such as 31 November or 29 February 2100, is refused with `That day is not on the calendar.` A stored end of `secret-value` does not open the file. The audit row `guest.before` names the role they had, including `editor` or `none`. `guest.after` names the guest role and the end date. Neither row includes the file body. `guest_review` lists those grants for the owner of the file. A permanent share is left out. The guest and anyone who does not own the file get an empty review. `POST /api/drive/items/{id}/guest` calls that share. The role is read as text and must be `viewer` or `commenter`. Any other word, including `secret-value`, is refused with `A guest share is a viewer or a commenter.` and the word is not repeated. `GET /api/drive/guests` returns the owner's review. A cluster test requested both routes. A role of `secret-value` was refused and was not repeated. An end date of `secret-value` was refused and was not repeated. Maya's review then listed Sam as a viewer until `2099-01-03T00:00:00.000Z` and did not include the file text `North bed`. Sam's own review was empty. The share dialog does not show these routes.

`externalShareReview` counts grants for people who are not members. Ada is listed. Sam, a member, is not. A blank name is counted and not listed. The note says people outside this organization still have access. It does not include a principal id or a file name. A guest whose end date has passed is left out. On 2026-11-01, an end of 2026-01-01 is not listed, and an end of 2026-12-01 still is. A date that is not a real day is still listed, and that date is not in the note. The list passed in is not changed. This note was not added to the share dialog or the Admin page.

A file with no name says `You own this item.` The item id is not in that sentence. A grant through a group says `You have access from a group on “Beds”.` when it comes from that folder, and `You were given access through a group.` when it is on the item. The group id is not in the sentence. A grant to the person still says `You were given access on this item as a viewer.` A group grant names the same role, so an editor sees `as an editor`. A role that is not one of those words says `as another role`, and that other word is not repeated. An expired grant still says `Your access has expired.` and does not add a role. The share dialog shows this sentence. It was not opened in the browser.

`folderMovePreview` says who would gain or lose access if a file moved into another folder. Priya is on the destination and would gain access. Sam’s access comes from the current folder and would be lost. Ada’s direct grant stays. The note says `This move changes who has access.` A move that only keeps a direct grant says `This move does not change who has access.` A new person whose name is blank still changes access, and the note does not include that person's id. Principal ids are not in the result. The lists passed in are not changed, and the file is not moved. The Move dialog reads the file and the destination, then shows that note before the file moves. A person whose grant has expired is left out of the note. If the grants change before Move here, the dialog says `The access plan changed. Review it again.` and does not move the file. An access read that fails says `The access plan could not be read.` `commitFolderMove` accepts that preview only while the grants are unchanged. A stamp of `secret-value` is refused with `The access plan changed. Review it again.` and that word is not in the refusal. The file is still not moved.

`shareChangePreview` says what a share would do before it is written. Priya would change from editor to viewer. A role that is not viewer, commenter, responder, editor, or owner is called another role, and that other word is not repeated. Responder and owner are named. A blank name says Someone. The share dialog shows that sentence and waits for Apply this access change. Cancel leaves the grant as it was.

`plan_editor_policy` lists each direct editor grant on a file or folder this person owns. Sam's editor grant on Garden would become viewer, including on the watering rota inside it. Priya's viewer grant is left out. The plan does not include the file body. A stamp that is not the current plan says `The access plan changed. Review it again.` and does not repeat that stamp. Applying the matching plan makes Sam a viewer. `rollback_editor_policy` sets those grants back to editor while each one is still a viewer. If Sam was changed to a commenter, the rollback writes nothing and Sam stays a commenter. The recovery sentence is `Set each changed grant back to editor.` This covers files this person owns. It is not an organization-wide policy. The Admin page does not run it.

A responder can add a response and cannot replace the questions. An answer for a field that is not a question is left out. The question list passed in stays as it was. On the node, a responder also cannot change any other part of the form while appending a response. A title `secret-value` is refused, and the saved form does not contain it. The submit keeps the title already on the form, `Beds`, and appends the response. A choice answer has to be one of the listed choices. ` Beds ` is stored as `Beds`. Another answer is refused with `Plot size must be one of the choices`, and that sentence does not include the refused answer. The listed choice on the question stays ` Beds `. A grid answer ` Mon ` and ` Yes ` is stored as `Mon` and `Yes`. Another column is refused with `Which days? must be one of the columns`, and that sentence does not include the refused answer. The listed row and column stay spaced.
