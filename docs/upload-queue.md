# Upload queue

A storage budget refuses a file that would not fit. The response is `SuiteDrive does not have room for this file.` and the saved file stays. A budget that is not a whole number of bytes says `The storage budget is not a whole number of bytes.` and does not repeat the value. A full SuiteDrive, an expired sign-in, and a file the person cannot change are not retried on a timer. A SuiteDrive node that answers 429 stores `SuiteDrive is busy with other uploads.` and `Wait, then retry this file. This copy stays on this device.` It is not retried on a timer. A missing file stores `That SuiteDrive file is not there.` and `Check the folder, then retry this file. This copy stays on this device.` It is not retried on a timer. A refusal to change the file stores `You cannot change this SuiteDrive file.` and `Ask for access, then retry this file. This copy stays on this device.` The stored note is `SuiteDrive does not have room for this file.` or `SuiteDrive needs a sign-in before this file can upload.` The server's own sentence is not stored. Releasing that file makes it due. Another file keeps its own schedule. A conflict stores `The SuiteDrive copy changed.` An unreachable SuiteDrive stores `SuiteDrive could not be reached.` The reported sentence, including `secret-value`, is not stored.

`runDueUploads` tries each file that is due. If Beds is unreachable, that failure stays on Beds and Paths is still uploaded. Paths is then removed from the queue. A second pass at the same time does not upload Paths again, because it is no longer due. Beds waits for its own retry time.

Retry sync still uploads the open file. It also retries every other failed upload that is due. A failed read of Beds does not stop Paths.

A file with no SuiteDrive link is `local`. Its label stays `Saved on this device`, `Saved to file`, or `Draft saved · choose Save As`. It is not `pending-sync`. A file that has a SuiteDrive link and a newer local revision stays `pending-sync`, labeled `Saved on this device · not yet on SuiteDrive`. The status line was not opened in the browser. Each library row uses that same label. A file with no SuiteDrive link reads `Saved on this device`. A matching SuiteDrive revision reads `Saved to SuiteDrive`. A newer local revision reads `Saved on this device · not yet on SuiteDrive` and does not say it was saved to SuiteDrive. The file id is not shown. At `http://127.0.0.1:5173/` the library links included `Untitled document Saved on this device`. Those files were already on this computer. No SuiteDrive file was opened in that check.

A retry starts after the bytes the server has already accepted. A 2,500-byte file with 1,000 bytes accepted and 1,000-byte slices has its next slice from 1,000 to 2,000. A failure keeps that place. When every byte is accepted, there is no further slice. A stored count that is not a whole number of bytes is ignored. This records the place. The due runner does not call the sender again when every byte is already accepted. An empty file is sent as `bytes 0-0/0` and becomes a version. It is not sent as a separate whole-body upload. After the server accepts those zero bytes, it is not sent again. After the server accepts those zero bytes, it is not sent again. A file with bytes still waiting is handed to the sender with that place. The SuiteDrive save sends that slice with a content range and keeps the accepted count. The file becomes a version when the last slice arrives. The accepted part is written under the blob directory, so opening the store again can take the next slice. A finished upload removes that part. `PUT /api/drive/items/{id}/content` with `Content-Range` accepts the first slice and stores the file when the last slice arrives.

A finished upload records the time and removes the file from the queue. The admin note says `The last successful upload was at 2026-11-01T00:00:00.000Z.` when that time is known, and `No upload has succeeded from this browser.` when it is not. The file id is not stored with the time. A stored value that is not a whole number of milliseconds is ignored. A blank, a fraction, and a negative time are left off the note. The admin page was not opened in the browser.

When the same paragraph changed on both sides, Keep both parts stacks the local paragraph and then the other one. `North` and `secret-value` both stay. Leaving them separate still produces no combined document, and that explanation does not repeat the paragraph. Each source copy stays as it was. The conflict bar was not opened in the browser.

Keep both parts on a spreadsheet adds the other copy of a changed sheet. The open sheet stays `North`. The added sheet is `Sheet1 (other copy)` and its cell stays `secret-value`. If that other-copy sheet is already in the workbook and holds different cells, the remote sheet is added under the next free id as `Sheet1 (other copy 2)`. The sheet that was already there stays. Cells are not merged. A spreadsheet is still not combined when Keep both parts is not chosen. The files passed in stay as they were. A chart on the other sheet is kept on that copied sheet. The chart title stays `Fees`, and its source range names the copied sheet. A pivot on the other sheet is kept the same way. The pivot title stays `Sales`, and its source and result name the copied sheet. The conflict bar was not opened in the browser.

Keep both parts on a presentation adds the other copy of a changed slide. The open slide stays `North`. The added slide is titled `Slide (other copy)` and its title text stays `secret-value`. If that other-copy slide is already in the deck and holds different objects, the remote slide is added under the next free id as `Slide (other copy 2)`. The slide that was already there stays. Objects are not merged. The deck passed in still has one slide. A master object that is only on the other deck is kept. The open master's background stays `#ffffff`, and the added object stays `Beds`. The other deck still has its own background. The conflict bar was not opened in the browser.

Keep both parts on a form adds the other copy of a changed response and a response that only the other copy has. The open response stays `North`. The changed response is stored again under a new id, and its answer stays `secret-value`. A new response `West` is added. Questions are not merged. When the questions differ, both versions stay separate. The form passed in still has one response. The conflict bar was not opened in the browser.

A document merge keeps comment threads from the copy that changed them. Local text `ONE` stays, and the other copy's thread `Water the beds` stays on the combined document. Comments added on each copy combine when each thread has its own id. A paragraph style changed on one copy and a comment added on the other both stay. A thread both copies rewrote stays separate. When both copies change those settings, both versions stay separate and the notice does not include the thread text. The copies passed in are not changed.

Named cells can be taken from the other spreadsheet. `B1` becomes `secret-value` and `A1` stays `North`. `B1:B2` also takes `B2` and leaves `A1`. `Fees!B2:C2` takes both cells from the Fees sheet. A range of more than 256 cells says `Name a smaller range.` and does not repeat the address. An address `secret-value` is refused with `Name a cell, such as B2.` and that word is not in the message. `Fees!B2` takes that cell from the Fees sheet on the other copy and leaves the first sheet. A sheet name that is not on the other copy says `That sheet is not in the other copy.` and does not repeat the name. The spreadsheet passed in stays `Bean` in `B1`. The conflict bar asks for those cells. A bad address shows `Name a cell, such as B2.` and does not repeat the address. Taking `B1` and `A1` says `Those cells were taken from the other copy.` The conflict bar was not opened in the browser.
