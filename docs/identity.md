# Sign-in sessions

A session cookie or bearer token is accepted only while its `expiresAt` is still ahead of the node clock and the session row is still in SuiteDB. Deleting the row, which an administrator already does when ending someone's sessions, makes the next request anonymous.

`auth.idle_secs` in the node configuration adds a second limit. A session whose `updatedAt` is older than that many seconds is refused even if `expiresAt` has not arrived. When `idle_secs` is omitted, only `expiresAt` applies. An `updatedAt` that is not a UTC timestamp is treated as idle once the limit is set, so a broken clock value does not stay signed in. A date that is not a real day, such as 31 February, does not keep the session. The web decision refuses that expiry and treats that activity time as idle. 29 February 2024 still signs in. The expiry is refused, and an activity time on that day is idle when an idle limit is set. `/api/node/info` reports that limit as `auth.idleSecs`, or null when it is not set. The web app, which the desktop app also loads, uses the same accept, expiry, and idle decision before it treats a stored sign-in as current. A stored sign-in that has no end time and no idle limit is left as it was. Sign-in still does not talk to an identity provider.

`--no-auth` still starts a node with no accounts. That local mode is unchanged.

A device name with a line break is shown as `Unnamed device`. The stored name stays, and the break is not shown. `GET /api/node/sessions` lists the signed-in person's sessions: id, created time, updated time, expiry, and a user agent of at most 120 characters. The session whose bearer matches is marked current. The token is not in the list. A user agent that contains the current token is left blank. The stored agent stays as it was. `DELETE /api/node/sessions/{id}` ends that person's session. The current one is marked this device and has no sign-out button. Rotating a session says the new token is not shown. A session id of `secret-value` is not written in the list. The Admin page was not opened in the browser. `revoke_lost_device` ends the signed-in person's sessions whose user agent is exactly the device name. Signing out `Lost phone` ends Sam's phone token and leaves the garden browser token. Priya's session with the same device name still signs in. The response is the count `ended`, not the device name. `verify_signed_assertion` accepts an assertion only when the Ed25519 signature matches the configured public key. A changed subject, a key that does not match, or a subject that contains a line break says `the assertion is not signed`. That sentence does not include the subject. A signature that matches is still refused when the assertion is expired, replayed, or for another issuer or audience. This does not sign anyone in and does not contact the provider.

`accept_assertion` rejects an expired assertion, a second use of the same `jti`, a different issuer, and a different audience. JWT verification calls that check when the token has a `jti`. The second use of that token is rejected. A token with no `jti` can be used again. A token for another audience is rejected. `link_subject` refuses to attach an assertion to an account that is already linked to another subject. JWT verification calls it when the token carries `oidc_sub` and the user already has an `account` row whose provider is `oidc`. A different subject is rejected. The same subject is accepted. A token without `oidc_sub` is not checked. This does not create the account row, and it does not talk to an identity provider.

`link_subject` also refuses a subject that contains `@`. `secret-value@gardenclub.org` is not an account id, and the error does not contain `secret`. `external_identity_id` keeps `https://idp.example` and `ada` together. An email-shaped subject is refused the same way. This does not create the account row, and it does not talk to an identity provider.

A `jwks` row whose `expiresAt` is at or before the node clock no longer verifies a JWT, even when the signature matches. An expiry that is not a real UTC instant, such as `secret-value` or 31 November, does not verify either. A clock that is not a real UTC instant does not keep a dated key signing. The error says the key has been rotated and does not include the private key. A row with no `expiresAt` still verifies. This reads the stored row. It does not fetch new metadata from an identity provider.

When an organization row's `metadata` lists `domains`, the JWT email host must be one of those names. `sam@gardenclub.org` matches `gardenclub.org`. `sam@mail.gardenclub.org` does not. The local part is not proof of ownership: a matching email with a different `oidc_sub` is still an unsafe link, and a successful check does not create an account row. The error does not include the email. A node with no domain list still accepts a token that has no email. This does not fetch metadata from an identity provider.

When an organization row's `metadata` sets `mfa` to true, the JWT must include `amr` with the exact method `mfa`. A token that only lists `pwd` is refused with `This organization requires a second factor.` The error does not include the other method names. That refusal does not use up the token's `jti`, so the same token id is accepted once `mfa` is present. A later repeat of that id is still a replay. This does not enroll a passkey and does not talk to an identity provider. A node whose organizations do not set `mfa` is unchanged. `--no-auth` is unchanged.

This does not add SAML, OIDC federation, or passkey enrollment. JWTs are still checked for the `suiteleaf` issuer and audience in `crates/suiteleaf-node/src/auth.rs`.

`SUITELEAF_EMERGENCY_CODE` opens one emergency session for an existing administrator. `POST /api/node/emergency` takes that person's id, the code, and a reason. The session lasts 15 minutes. The same code does not open a second session. A person who is not an administrator, including a banned administrator, is refused and the code stays unused. A reason that contains the code is refused. The audit row is `emergency.sign-in`. It records the person and the reason, not the code. The session token is not the code. When the variable is unset, the route refuses and writes no audit row. `--no-auth` does not set the variable. This does not talk to an identity provider.
